# Шинэ байгууллагын онбординг — дараалал ба логик

Шинээр нэгдэж буй компани **яг ямар дарааллаар юу хийхийг** энд тодорхойлов.
Bonum болон LIME талд шинэ мерчант нэмэх **автомат систем одоогоор байхгүй**
тул урсгал хагас гар ажиллагаатай: бид хүсэлтийг имэйлээр илгээж, хариуг
платформын админ бүртгэнэ.

## Оролцогчид

| Тал | Үүрэг |
|---|---|
| **Компани (tenant OWNER)** | Мэдээллээ үнэн зөв гүйцэд бөглөх, ТЕГ дээр өөрөө бүртгүүлэх/зөвшөөрөх, Bonum credentials-ээ оруулах |
| **billingservice.mn (платформ)** | Хүсэлтийг Bonum/LIME рүү имэйлээр илгээх, хариуг бүртгэх, модуль идэвхжүүлэх |
| **Bonum** | Мерчант гэрээ, терминал + данс холболт, credentials олгох |
| **LIME** | POS API instance дээр merchant нэмэх |
| **ТЕГ (татварын алба)** | Компанийн POS бүртгэл, merchantTin/posNo олголт |

## Дараалал (эцсийн, зөв урсгал)

```
 1. Бүртгүүлэх (данс үүсгэх) → OWNER эрх автоматаар
 2. Тохиргоо → байгууллагын мэдээлэл ГҮЙЦЭД бөглөж хадгалах:
       нэр · регистр · хаяг · утас · имэйл          (2 талд хоёуланд хэрэгтэй)
       банк · дансны дугаар · дансны нэр            (Bonum данс холболтод)
    ⚠ Мэдээлэл дутуу бол хүсэлт огт илгээгдэхгүй (ANKET_INCOMPLETE).

 ── eBarimt салаа ─────────────────────────────────────────────
 3. ТАТВАРЫН АЛБА (системээс ГАДУУР, компани өөрөө):
       a. ТЕГ-т өөрийн POS-оор бүртгүүлэх
       b. Өөрийн эрхээр ТЕГ-ийн порталд нэвтэрч зөвшөөрөл өгөх
    ⚠ Энэ алхамгүйгээр LIME бүртгэж чадахгүй — заавал ЭХЭЛЖ хийнэ.
 4. Тохиргоо → «eBarimt (LIME)» хүсэлт илгээх
       → бид ONBOARDING_LIME_EMAIL руу компанийн мэдээллийг илгээнэ
 5. LIME instance дээр merchant нэмэгдэж, merchantTin/posNo хариу ирнэ
       → merchantTin (=ТТД) нь регистрээр АВТОМАТААР бөглөгдсөн байна
         (api.ebarimt.mn/api/info/check/getTinInfo?regNo=)
       → үлдсэн posNo/branchNo/districtCode-ыг Интеграци → «eBarimt (POS API 3.0)»
         картад оруулна (эсвэл партнёр /partner/requests-ээс хариугаа бөглөхөд
         автоматаар бичигдэнэ)
       → админ /admin/requests дээр APPROVED болгоно
          ✓ EBARIMT модуль автоматаар идэвхжинэ
       → GET /api/v1/receipts/provider-info-оор /rest/info дээр TIN харагдаж
         буйг шалгана

 ── Bonum салаа (eBarimt-тэй зэрэг явж болно) ────────────────
 6. Тохиргоо → «Bonum Gateway» хүсэлт илгээх
       → бид ONBOARDING_BONUM_EMAIL руу анкет + WEBHOOK URL-ийг илгээнэ
 7. Bonum гэрээ баталгаажиж Terminal ID / Secret Key / Checksum Key имэйлээр ирнэ
       → админ Интеграци → «Bonum төлбөрийн гарц» картад оруулна
         (нууцууд AES-256-GCM шифрлэгдэж хадгалагдана, дахин харагдахгүй)
       → «🔌 Холболт шалгах» дарж токен авагдаж буйг баталгаажуулна
       → админ хүсэлтийг APPROVED болгоно

 8. ТУРШИЛТ: 1₮-ийн нэхэмжлэх үүсгэж SMS линк → төлөлт → eBarimt гарч буйг шалгах
 9. Ажиллагаанд: нэхэмжлэх → манай линк SMS-ээр → төлөгч дарахад Bonum линк
    (шинээр/дахин) үүсэж → төлөлт → invoice-check баталгаажилт → ledger →
    eBarimt (тухайн компанийн ӨӨРИЙН TIN/posNo-оор) автоматаар
```

## Шалгасан логикийн асуудлууд ба засварууд

Энэ дарааллыг кодтой тулгаж дараах асуудлуудыг илрүүлж зассан:

1. **Bonum credentials глобал байсан** ❌ → Бүх компанийн төлбөр НЭГ терминал
   (платформын данс) руу орох байсан. Bonum дээр компани бүр өөрийн данстай
   терминал авдаг тул **tenant бүр өөрийн Terminal ID/Secret/Checksum-тэй**
   болгож зассан (шифрлэгдсэн хадгалалт, terminal тус бүрийн token кэш).
   Env-ийн credentials нь платформын өөрийн (fallback) терминал болж үлдсэн.

2. **EBARIMT модуль мартагдах эрсдэл** ❌ → Модуль унтраатай байх үед хийгдсэн
   төлбөрт баримт `NOT_REQUIRED` болж, **хожим нөхөн үүсдэггүй**. Компани
   идэвхжүүлэхээ мартвал баримт алдагдана. Засвар: eBarimt хүсэлтийг админ
   APPROVED болгомогц EBARIMT модуль автоматаар идэвхжинэ; туршилтын
   нэхэмжлэхээ (алхам 8) заавал үүнээс ХОЙШ илгээх дараалал баримтад тусгав.

3. **Дутуу анкеттай хүсэлт** ❌ → Урд нь юу ч шалгагдахгүй байсан. Одоо хүсэлт
   илгээхэд шаардлагатай талбарууд (регистр, хаяг, утас, имэйл; Bonum-д
   нэмээд банк/данс) серверт хатуу шалгагдаж, дутууг нь монголоор нэрлэж
   буцаана — 2 талд буруу/дутуу мэдээлэл явахаас сэргийлнэ.

4. **Webhook бүртгэл терминал бүрд** — Bonum-ийн онбординг имэйлд WEBHOOK
   URL-ээ хамт илгээдэг болгосон: шинэ терминал үүсэхдээ callback-тайгаа
   бүртгэгдэнэ (мартагдвал ч poll backstop төлбөрийг барьж авна).

5. **LIME-ийн posNo дундаа хэрэглэх эрсдэл** — ТЕГ-ийн дүрмээр компани бүр
   өөрийн merchantTin+posNo-той. Adapter баримт үүсгэхийн өмнө `/rest/info`
   дээр тухайн TIN бүртгэлтэй эсэхийг шалгаж, бүртгэлгүй бол ойлгомжтой
   алдаагаар зогсоно (өөр компанийн posNo-оор баримт гарахгүй).

6. **Хуучирсан Bonum линк** — линк богино хугацаатай тул SMS-ээр зөвхөн манай
   линк явдаг; төлөгч хожим дарахад төлөгдөөгүй бол шинэ Bonum линк автоматаар
   үүснэ, төлөгдсөн байвал (callback алдагдсан ч) provider-оос дахин шалгаж
   «Төлбөр амжилттай» харуулна. (Өмнөх PR-д хийгдсэн, энд дарааллын нэг хэсэг.)

### Мэдэгдэж буй үлдэгдэл (дараагийн ээлж)

- **B2B eBarimt**: төлөгч байгууллага ААН-ийн баримт (өөрийн TIN дээрээ) авах
  сонголт төлбөрийн хуудсанд одоогоор алга — бүх баримт иргэний (B2C) горимоор
  гарна. `EbarimtReceipt.receiptType/payerRegNo` талбарууд бэлэн тул төлбөрийн
  хуудсанд «ААН-ийн баримт» сонголт нэмэхэд суурь өөрчлөлт шаардахгүй.

## Админ хэрэглэгч (платформын ажилтан)

- Нэвтрэх: `admin@billingservice.mn` / `Admin123$` (seed; production дээр
  солино). `User.isPlatformAdmin=true` туг нь `/admin/requests` хуудас болон
  `/api/v1/admin/integration-requests*` endpoint-уудыг нээнэ.
- Админ хуудас зөвхөн бүртгэлийн хүсэлтүүдийг харуулна: имэйл дахин илгээх,
  баталгаажуулах, татгалзах (шалтгаантай).
