# Бизнес дүн шинжилгээ — 4 үйлчилгээний загвар ба системийн одоогийн байдал

Огноо: 2026-08-12 · Хамрах хүрээ: `apps/api` + `apps/web` кодын сан бүхэлдээ,
PRD (v1.0), ONBOARDING.md, INTEGRATIONS.md, RISKS.md баримтуудтай тулгасан.

Зорилго: Захиалагчийн шинээр цэгцэлсэн **4 үйлчилгээний бизнес загвар** одоогийн
системд хэр дэмжигдэж байгааг үйлчилгээ тус бүрээр шалгаж, зөрүү (gap)-г
нэрлэж, сайжруулалтын ажлыг эрэмбэлэн гаргах.

---

## 1. Зорилтот бизнес загвар (цэгцэлсэн хувилбар)

**Хэрэглэгч:** компани, ТББ, жижиг дунд үйлчилгээ эрхлэгчид.

**Нэгдсэн бүртгэл (бүх үйлчилгээний суурь):**

1. Байгууллага өөрөө өгнө: регистрийн дугаар, банкны данс, харьяа татварын
   газар / хаяг (дүүрэг).
2. Бусад шаардлагатай мэдээллийг нээлттэй API-аар автоматаар таньж
   боловсруулж авна (ТТД, НӨАТ статус, байгууллагын нэр г.м.).
3. Нэгдсэн байгууллагын профайл хадгалагдана.
4. eBarimt (Онлайм нетворк / LIME операторын сувгаар) татварын системд
   бүртгэх + Bonum төлбөрийн гарцад бүртгэх **цогц үйлдэл** хийгдэж,
   төлбөртэй үйлчилгээ авах бэлтгэл хангагдана.

**4 үйлчилгээ (давхардуулан ч, тус тусад нь ч авч болно, сонголт ойлгомжтой):**

| # | Үйлчилгээ | Үнийн загвар |
|---|---|---|
| 1 | Excel файлаас нэхэмжлэх үүсгэж SMS-ээр илгээх | 100₮ / msg (нэг msg 2 хэсэгт хуваагдаж явж болно) |
| 2 | API-аар холбогдон нэхэмжлэх үүсгэж SMS илгээх (Excel-гүй) | Байгууллага бүр харилцан адилгүй тохиролцооны үнэ; эхний үйлчлүүлэгч 75₮/msg |
| 3 | SMS-гүй — үйлчлүүлэгчийн өөрийн системд eBarimt холбох (API) | Интеграцийн зардал 100,000₮ (нэг удаа) + сарын 20,000₮–100,000₮ (сарын eBarimt-ийн тооны хязгаараар шатлалтай) |
| 4 | POS terminal апп дээрээс eBarimt үүсгэх | POS терминал тус бүр 20,000₮/сар |

## 2. Ерөнхий дүгнэлт (TL;DR)

- **Суурь (нэгдсэн бүртгэл + автомат таних):** ихэнх нь **бодитоор байна** —
  регистр → ТТД/НӨАТ статус автомат татах, дүүргийн код сонгох, Bonum/LIME
  хүсэлт автомат үүсэх урсгал ажиллаж байна. Гэхдээ Bonum тал бүрэн гар
  ажиллагаатай (имэйл) бөгөөд "нэг цогц үйлдэл" гэхээсээ хагас автомат.
- **Үйлчилгээ 1 (Excel+SMS):** техникийн урсгал **бүрэн байна**, гэхдээ үнэ нь
  таны загвартай таарахгүй — одоо 25₮/segment (глобал), 100₮ гэсэн ойлголт алга.
- **Үйлчилгээ 2 (API+SMS):** API нэхэмжлэх endpoint **байна** (`POST
  /partner/invoices`), гэхдээ **tenant тус бүрийн тохиролцооны үнэ огт
  байхгүй** — үнэ нэг глобал тохиргоо. 75₮-ийн гэрээт үнийг өнөөдөр системд
  оруулах боломжгүй.
- **Үйлчилгээ 3 (eBarimt API интеграц):** **байхгүй.** eBarimt баримт нь
  зөвхөн манай нэхэмжлэх → төлбөр → гүйлгээний гинжний "сүүл" болж үүсдэг;
  гаднын систем шууд баримт үүсгэх endpoint, сарын тооны хязгаар, шатлалтай
  үнэ, нэг удаагийн интеграцийн төлбөр аль нь ч алга.
- **Үйлчилгээ 4 (POS terminal):** **байхгүй.** POS гэдэг нь өнөөдөр зөвхөн
  billing-ийн тоо (quantity × 20,000₮) — терминалын бүртгэл, төхөөрөмжийн
  нэвтрэлт, POS апп-д зориулсан endpoint огт алга.
- **Үнэ тооцооллын хөдөлгүүр:** хэрэглээ хэмжигддэг (meter) ч, **сар хаах,
  өөрийн үйлчилгээний нэхэмжлэх үүсгэх, төлбөр авах механизм байхгүй** —
  өөрөөр хэлбэл billing SaaS маань өөрийнхөө үйлчилгээний төлбөрийг одоогоор
  нэхэмжилж чадахгүй. Шинэ загварыг нэвтрүүлэхэд энэ нь хамгийн том дутагдал.

Товч байдлаар: **суурь бүртгэл 80%, үйлчилгээ 1 = 85%, үйлчилгээ 2 = 60%,
үйлчилгээ 3 = 25%, үйлчилгээ 4 = 5%, тарифын хөдөлгүүр = 30%** бэлэн гэж
үнэлж болно.

## 3. Нэгдсэн бүртгэл / онбординг — тулгалт

### Байгаа (кодоор баталгаажсан)

| Шаардлага | Байдал | Баримт (код) |
|---|---|---|
| Регистрийн дугаар, банк (нэр/данс/эзэмшигч), хаяг, төлөөлөгч | ✅ Tenant профайлд бүгд бий | `prisma/schema.prisma:44-96`, `tenants.controller.ts` `PATCH /tenant` |
| Регистр → ТТД автомат таних | ✅ `api.ebarimt.mn/api/info/check/getTinInfo?regNo=` | `providers/ebarimt-registry.service.ts:70` |
| НӨАТ суутган төлөгч / чөлөөлөгдсөн статус автомат | ✅ `getInfo?tin=` → `vatPayer/freeProject/cityPayer` | `ebarimt-registry.service.ts:75-95` |
| Дүүрэг/байршлын код сонгуулах (татварын харьяалал) | ✅ `getBranchInfo` лавлах, 24ц кэш, UI сонгогч | `ebarimt-registry.service.ts:103-128`, `GET /tenant/districts` |
| eBarimt-д мерчант бүртгэх (операторын API) | ✅ Бодит `saveOprMerchants` дуудлага (ТЕГ) | `ebarimt-operator.service.ts:98-151` |
| posNo/branchNo автомат татах | ✅ `/rest/info`-оос discover + sync | `posapi-ebarimt.adapter.ts:138-149`, `POST /integrations/EBARIMT/sync` |
| Bonum + LIME хүсэлт автомат үүсэх | ✅ Анкет гүйцэд болмогц 2 хүсэлт автоматаар имэйлээр илгээгдэнэ | `integrations.service.ts:229-265` (autoSubmit) |
| Onboarding wizard (4 алхам) | ✅ Байгууллага → Банк → eBarimt → Баталгаажуулалт | `web/.../onboarding/page.tsx` |

### Зөрүү / анхаарах зүйл

1. **"Цогц нэг үйлдэл" биш, хагас гар ажиллагаатай.** Bonum талд мерчант
   үүсгэх API байхгүй тул урсгал: имэйл → гэрээ → credentials гараар буцаж
   ирэх → админ бүртгэх. LIME тал операторын API-тай ч тэр товчнууд
   **зөвхөн админд** нээлттэй (`integrations.controller.ts:71` `@AdminOnly`),
   өөрөөр хэлбэл байгууллага өөрөө "бүртгүүлэх" товчоо дарж чадахгүй.
2. **Оролцогчийн хүлээлтийг UI дээр удирдах хэрэгтэй** — бүртгэл хэдэн цаг/
   өдөр хүлээгдэхийг (Bonum гэрээ, ТЕГ баталгаажуулалт) харуулах progress
   төлөв бий (`IntegrationRequestStatus`), гэхдээ хэрэглэгчид "хаана, юуг,
   хэн хийхийг" харуулсан нэгдсэн статус самбар сул.
3. **Демо орчны анхдагч тохиргоо бүгд mock** (`EBARIMT_PROVIDER=mock`,
   `EMAIL_PROVIDER=mock`, `SMS_PROVIDER=mock`) — production дээр SMTP,
   `EBARIMT_OPR_API_KEY`, CallPro түлхүүрүүд заавал тохируулагдана.
4. "Татварын газар бүртгэлтэй" гэдгийг **дүүргийн код** төлөөлж байгаа —
   энэ нь eBarimt-ийн шаардлагад хүрэлцээтэй, нэмэлт талбар шаардлагагүй.

**Дүгнэлт:** Суурь бүртгэлийн урсгал бизнес загвартаа нийцтэй, гол сайжруулалт
нь (а) байгууллага өөрөө ТЕГ бүртгэлийн хүсэлтээ өгдөг болгох, (б) нэгдсэн
онбординг статус самбар, (в) Bonum-ийн гар алхмуудыг аль болох автоматжуулах.

## 4. Үйлчилгээ тус бүрийн тулгалт

### Үйлчилгээ 1 — Excel → нэхэмжлэх → SMS (100₮/msg)

**Байгаа:** Excel/CSV импортын бүрэн wizard (валидаци → preview → approve →
илгээлт, 5000 мөр/5MB), нэхэмжлэхийн state machine, богино линк, SMS segment
тооцоолол (кирилл UCS-2 70/67 — таны "нэг msg 2 хуваагдаж явж болно" гэдэг
яг энэ), кирилл→латин хөрвүүлж өртөг хагаслах сонголт, хэрэглээний meter
(`SMS_SEGMENT_SENT`), CallPro бодит SMS adapter.

**Зөрүү:**

| Асуудал | Дэлгэрэнгүй |
|---|---|
| Үнэ 25₮/segment ≠ 100₮ | `billing.service.ts:13-18` `SMS_PER_SEGMENT: 25`. 100₮ гэсэн тариф хаана ч алга. |
| "100₮ нь юуных вэ?" тодорхойгүй | 100₮ = нэг **илгээлт** (2 хэсэгт хуваагдсан ч 100₮) үү, эсвэл **хэсэг тус бүр** үү? Систем одоо segment-ээр тоолдог. ⚠ Шийдвэр хэрэгтэй (§6-Q1). |
| Импортын preview үнэ hard-code | `imports.service.ts:215` — `* 25` гэж бичсэн, админ үнэ өөрчилбөл preview хуучин үнээр гарна (алдаа). |
| Landing калькулятор үнэ hard-code | `pricing-calculator.tsx:6-9` — API-гаас уншдаггүй тул үнэ өөрчлөхөд landing зөрнө (алдаа). |
| SMS модулийн toggle гоёл төдий | SMS модуль унтраасан ч илгээлт хаагддаггүй (`TOGGLABLE`-д бий ч enforcement алга). |

### Үйлчилгээ 2 — API нэхэмжлэх + SMS (байгууллага бүр өөр үнэ, эхнийх 75₮)

**Байгаа:** API түлхүүр (`bsk_…`, 5 хүртэл, hash хадгалалт), `POST
/partner/invoices` (нэхэмжлэх үүсгээд SMS илгээгээд pay_url буцаана), `GET
/partner/invoices/:id`, outbound webhook (`payment.succeeded`,
`receipt.created`, HMAC гарын үсэгтэй), Developers UI.

**Зөрүү:**

| Асуудал | Дэлгэрэнгүй |
|---|---|
| **Tenant тус бүрийн үнэ байхгүй** | Үнэ нэг глобал `PlatformSetting('pricing')` мөр. 75₮-ийн гэрээт үнэ оруулах газар алга. Энэ бол Үйлчилгээ 2-ын гол хаалт. |
| Excel ба API сувгийн үнэ ялгардаггүй | `SMS_SEGMENT_SENT` meter-т эх сурвалж (import/api/manual) бичигддэггүй тул 100₮/75₮ ялгаж тооцох боломжгүй. |
| API модуль зарлагдсан ч байхгүй | Landing дээр "SMS, eBarimt, POS, API — хэрэгтэйгээ л асаана" гэж бичсэн ч `API` модуль toggle/үнэ/enforcement алга. |
| API түлхүүрт scope алга | Түлхүүр бүх partner эрхтэй; үйлчилгээ 2 ба 3-ыг зэрэг нээхэд ялгах scope хэрэгтэй болно. |
| Idempotency-Key partner дээр хэрэгждэггүй | `IdempotencyKey` хүснэгт бий ч partner route ашигладаггүй — давхар нэхэмжлэх үүсэх эрсдэл. |

### Үйлчилгээ 3 — Өөрийн системд eBarimt холбох (100,000₮ + 20к–100к/сар шатлал)

**Байгаа (суурь):** POS API 3.0 бодит adapter (Онлайм нетворк/LIME операторын
загвар: операторын нэг posNo дээр олон мерчант, баримт `merchantTin`-ээр
ялгагдана — яг таны "Онлайм нетворк" сувгийн бүтэц), B2B/B2C баримт, НӨАТ
төрлийн автомат тодорхойлолт, retry, QR/сугалаа хадгалалтын хугацааны purge,
`RECEIPT_CREATED` meter.

**Зөрүү (үйлчилгээ болгох бүх зүйл дутуу):**

| Асуудал | Дэлгэрэнгүй |
|---|---|
| **Standalone баримт үүсгэх API байхгүй** | `POST /receipts` гэх endpoint алга; баримт нь Invoice→PaymentIntent→PaymentTransaction гинжгүйгээр **бүтцийн хувьд үүсэх боломжгүй** (`receipts.service.ts:37`, schema-д transactionId заавал). Шинэ endpoint + гүйлгээнээс ангид баримтын зам хэрэгтэй. |
| Сарын тооны хязгаар байхгүй | Ямар ч quota механизм алга — 20к–100к шатлалын суурь болох "сарын eBarimt тоо" хязгаарлагдахгүй. |
| Шатлалтай сарын үнэ байхгүй | Одоо eBarimt = 20,000₮ тогтмол. Шатлал (tier) тодорхойлох бүтэц алга (§6-Q2). |
| Нэг удаагийн интеграцийн төлбөр байхгүй | One-time fee гэсэн ойлголт billing-д огт алга. |
| Баримт цуцлах/буцаах API байхгүй | Гаднын систем баримт цуцлах (refund/return) хэрэгцээ гарна — port дээр ч, route дээр ч алга. |
| eBarimt-ийн авто retry scheduler алга | Retry нь зөвхөн дараагийн төлбөр эсвэл гар үйлдлээр өдөөгдөнө — API үйлчилгээнд background sweeper зайлшгүй. |

### Үйлчилгээ 4 — POS terminal апп eBarimt (20,000₮/терминал/сар)

**Байгаа:** `POS` модулийн toggle + `quantity` (0–100) × 20,000₮ гэсэн
**зөвхөн тооцооны мөр**.

**Зөрүү — бараг бүгд:**

| Асуудал | Дэлгэрэнгүй |
|---|---|
| Терминалын бүртгэл алга | `PosTerminal` загвар байхгүй — серийн дугаар, байршил, салбар, төлөв гэх мэт бүртгэлгүй; `quantity` нь чөлөөт тоо. |
| Төхөөрөмжийн нэвтрэлт алга | POS апп-ыг таних түлхүүр/токен, enrollment урсгал байхгүй. |
| POS-оос баримт үүсгэх endpoint алга | Терминалаас ирэх борлуулалт → eBarimt үүсгэх API байхгүй (Үйлчилгээ 3-ын standalone зам дээр суурилж болно). |
| Терминал тооноос хураамж автоматаар бодогддоггүй | Хураамж бүртгэлтэй терминалын тооноос гарах ёстой; одоо гараар оруулсан quantity-гээс гарна. |

## 5. Тарифын хөдөлгүүрийн нийтлэг зөрүү (бүх үйлчилгээнд нөлөөлнө)

Одоогийн бүтэц: глобал 4 үнэ (`BASE_FEE 20,000₮ / SMS 25₮ / EBARIMT 20,000₮ /
POS 20,000₮`, админ засварлаж болно) + хэрэглээний meter + сарын
**урьдчилсан тооцоо** (estimate) л байна. RISKS.md-д эдгээр үнийг "захиалагчийн
таамаг" гэж тэмдэглэсэн нь таны шинэ загвараар солигдох гэж буйг баталж байна.

Шинэ загварт дутагдаж буй чадварууд:

1. **Үйлчилгээний каталог** — таны 4 үйлчилгээ ≠ одоогийн 4 модуль
   (SMS/EBARIMT/POS/REMINDER). Ялангуяа Үйлчилгээ 1 ба 2 хоёулаа "SMS"
   модульд нийлчихсэн, Үйлчилгээ 3 нь EBARIMT модулиас (өөрийн төлбөрт
   баримт) тусдаа ойлголт. Каталогийг дахин загварчилж, байгууллага бүр аль
   ч хослолоор сонгодог, UI дээр маш ойлгомжтой байх шаардлага.
2. **Tenant түвшний үнэ (price override)** — 75₮ гэрээт үнэ, хүчинтэй огноотой.
3. **Нэг удаагийн төлбөр** — интеграцийн 100,000₮.
4. **Шатлалтай (tiered) сарын багц + quota** — 20к–100к / сарын баримтын тоо,
   хязгаар давахад юу болох (зогсоох vs нэмж тооцох) дүрэм.
5. **Сар хаах + өөрийн үйлчилгээний нэхэмжлэх (service invoice)** — одоогоор
   зөвхөн урьдчилсан тооцоо харагдана; нэхэмжлэх үүсгэх, төлүүлэх, хугацаа
   хэтрэлтийн урсгал алга. (Инээдтэй нь: систем өөрөө нэхэмжлэх илгээдэг
   платформ учраас өөрийн хураамжаа өөрийнхөө урсгалаар нэхэмжлэх боломжтой.)
6. **Meter-т эх сурвалж/үйлчилгээний код** — аль үйлчилгээний хэрэглээ болохыг
   ялгаж бичих (`source: import|api|pos`).

### P2 — Өсөлтийн шат

- Нэгдсэн онбординг статус самбар (Bonum/LIME/ТЕГ алхам бүрийн явц нэг дэлгэцэд).
- Quota-д ойртох үеийн анхааруулга (имэйл/SMS) + шатлал ахиулах upsell.
- Төлбөрийн хуудсанд B2B (ААН-ийн ТТД-тэй) баримтын сонголт (суурь нь бэлэн).
- Платформын хураамжийн авто нэхэмжлэл + сануулга (dunning) — өөрийн үйлчилгээгээр.
- Bonum онбордингийн гар алхмуудыг API гарч ирвэл автоматжуулах.

## 9. Эрх зүй / эрсдэлийн санамж (RISKS.md-тэй уялдсан)

- Платформ мөнгө хүлээж авахгүй SaaS-orchestrator загвар хэвээр — transaction
  fee / settlement split нэвтрүүлэх бол Монголбанкны дүгнэлт шаардлагатай
  (одоогийн 4 үйлчилгээ бүгд SaaS хураамж тул энэ загварт **асуудалгүй**).
- Production SMS-д CallPro гэрээ, sender ID баталгаажилт шаардлагатай; SMS
  доторх линк whitelisting-ийг CallPro-той урьдчилан тохирох (adapter-т
  "unverified link" алдааны боловсруулалт аль хэдийн бий).
- Тарифын өөрчлөлт бүр landing/калькулятор/биллинг гурвалд зэрэг тусдаг байх
  ёстой — P1 №8–9 үүнийг бүтцээр нь шийднэ.
- Платформын хураамжид НӨАТ тооцох эсэх (Q6) — нягтлан/татварын зөвлөхөөр
  баталгаажуулах.
